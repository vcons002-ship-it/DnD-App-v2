# Map walls and personal line of sight

The DM can now trace opaque walls over the existing map art. Each map saves its
own rectangles and line segments. Players see terrain and tokens only when their claimed character
has an unobstructed line of sight, in addition to the existing light/range and
fog rules. DM views remain unrestricted.

## Using it

1. Open **Walls** in the DM map toolbar and choose **Draw wall rectangles**.
2. Drag from one corner to the opposite corner, covering the painted wall's
   length and thickness. Release to save all four sides as one wall. Dragging
   in either direction works; Escape cancels an unfinished rectangle.
3. Leave gaps for doors. Nearby corners snap together; optional grid snapping
   uses the map's grid offset. Drawing works on the same plane in overhead,
   tilted and rotated views.
4. **Erase a wall** removes the whole rectangle when clicked anywhere inside it.
   **Undo last wall** removes the most recently saved rectangle or line.
   **Done** exits drawing.

For a diagonal or thin barrier, **Draw connected walls** remains available.
Click its start and each corner; each segment saves immediately. **Finish chain**
or Escape starts a separate chain.

The wall guides are visible to the DM while the wall tool is active. They do not
become visible lines on the players' map. DM tracing does not broadcast the
cursor, and cannot accidentally select/drag a creature or paint annotations.

## Visibility and lighting

- Walls block personal sight even in daylight or with environment effects off.
- Regular/heavy darkness retain the campaign's 60-foot unlit vision rule.
  Heavy darkness remains grayscale outside actual illumination.
- A distant illuminated area needs both a clear player-to-point sight line and
  a clear light-to-point path. A torch in the next room cannot reveal a creature
  through the wall. Placed light can enter through a doorway even if its source
  is around the corner. Unseen creatures' carried lights are omitted to avoid
  disclosing the carrier's identity or position in a lighting payload.
- Placed and carried lights cast wall-shaped shadows on terrain and mist.
  Miniatures receive only nearby lights with an unobstructed path to their base.
- Nearby torches and lanterns also cast shadows from the actual creature geometry
  onto the floor and other figures. Source position and height determine the
  direction and length. Dungeon lighting no longer casts the fixed sun shadow.
  Existing painted shadows in the map image are unchanged.
- Existing hidden flags and both fog layers still apply. Obscured creatures are
  removed from that player's server snapshot, so names and target lists do not
  disclose them. Encounter tags also use wall-aware party visibility.
- Turning off effects or switching to 2D tokens does not bypass visibility.

Walls currently represent opaque barriers of unlimited height. They do not add
3D scenery, prevent token movement, restrict attack rolls, or provide interactive
door/window states. Place lights slightly inside a room rather than exactly on
a wall line (a source on a barrier has no defined side and is occluded).

## Implementation and performance

`maps.walls` uses an idempotent migration with an empty-array default. Old saves
keep their previous behavior. The existing full-row backup/import path carries
walls with their map; legacy imports without the column default to no walls.
The DM-only incremental edit event validates coordinates, IDs, nonzero lengths,
session ownership and a 512-edge map limit. Each rectangle uses four edges, so
an all-rectangle map supports 128 rectangles. A rectangle is stored as one object
and expands to cached edges for visibility. Retried additions are idempotent.

`shared/mapWalls.ts` supplies the same segment intersections to the server's
visibility checks and the client's visibility polygons. Polygons are cached per
source and rebuilt for source/wall movement, not for camera motion or flicker.
The existing light-field pass uses clipped triangle fans with reusable GPU
buffers; no per-pixel wall-ray loop or extra full-scene pass is added. Figure
lighting rejects occluded sources before choosing its existing eight-light cap.

Detailed local shadows use up to four 512-pixel depth cube maps, selected by
their contribution at visible creatures. Other lights still illuminate normally.
The cache refreshes when casters or sources move; camera motion and brightness
flicker alone reuse it. This bounds memory and avoids a cube map for every placed
light. These shadows affect rendering, not the authoritative visibility rules.

## Verification

- Unit coverage: crossings, endpoints, narrow doorways, crossed-wall corners,
  malformed input, idempotence, cross-campaign rejection, saved map isolation,
  full/legacy backup restore, independent players, daylight/effects-off,
  darkvision versus illumination, movement, fog, hidden tokens and reveal tags.
- Rectangle coverage includes all four sides, solid interiors, reversed drags,
  cancelled drafts, atomic erase/undo and backup restore.
- Real production app: DM draws two rectangles and erases one; Druk and Vanec
  see opposite sides in separate browser sessions. Checks overhead/45 degrees,
  real 3D models, rejected player edits, reload persistence and a narrower 2D
  player viewport with effects off. Browser errors and shader errors are checked.
- Browser captures live in the Playwright output for the test titled
  `DM draws saved walls and each player sees their own lit side...`.
- Tests use disposable databases. The live campaign save/service is untouched.
- Recorded walkthrough: `DND_MOVEMENT_DEMO=1` with the Playwright test
  `rectangle wall walkthrough on the dungeon with personal sight and lanterns`.
  It traces the room's actual south doorway on the dungeon artwork and records
  Varis approaching Druk, entering, revealing the far corner, and backing out.
  It compares both player views, darkvision, Varis's moving lantern, opposite
  torch positions, and the same scene at 45 degrees. It also checks that the
  dungeon directional shadow is off and stationary cube maps are cached.
  `scripts/environment-preview/publish-walls.mjs <test-output-directory>` joins
  the recorded chapters and publishes a mobile video page on the DnD domain.

Physical phone frame rates have not been measured for the wall feature.
